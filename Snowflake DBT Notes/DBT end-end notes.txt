Big picture (1 minute)dbt Projects on Snowflake let you:Write SQL transformation logic (dbt models)Store & version it in GitRun dbt directly inside Snowflake (no external dbt Cloud / server needed)Schedule it using Snowflake TasksSnowflake treats your dbt code as a first‑class object called a DBT PROJECT.DBT Components:🔹 models/ (usually staging models)These are not just “as‑is raw copies”, but:Cleaned, standardised versions of raw tablesMostly 1‑to‑1 with raw tablesMinimal changesNo business logic✅ Typical actions here:Select required columnsRename columnsCast data typesStandardise values (upper/lower, trim)Handle nulls minimallyGoal:Make raw data safe and consistent for downstream use.--models (staging) should NOT be raw “as‑is copies”They should clean & standardise, even if lightly.Example :staging-- models/staging/stg_rmbsloan.sqlselect    request_id,    upper(master_trust_name_or_spv_prl003) as trust_name,    cast(current_balance_prl012 as number(18,2)) as current_balancefrom raw.rmbs_loan;marts/ (business / reporting layer)These are NOT as‑is data.This is where transformations, calculations, joins, aggregations happenypical actions here:Aggregations (sum, count, avg)Business logicDerived columnsJoins between staging modelsMetrics used by reports, dashboards, analysts📌 Goal:Produce business‑ready, consumption‑ready tables.-- models/marts/customer_metrics.sqlselect    reporting_period,    sum(current_balance) as total_balance,    count(*) as loan_countfrom {{ ref('stg_rmbsloan') }}group by reporting_period;notes:Snowflake encourages tables for marts, views for staging.--------------------------------------------------------------------------------------------Step 1: Understand what a “dbt project” isA dbt project is just a folder with:dbt_project.ymlSQL files under /modelsOptional tests & docs (YAML files)Each SQL file is a SELECT statement that creates a table or view in Snowflakeex:-- models/stg_customers.sqlselect * from raw.customers;model:A dbt model is only a SELECT statement:One SQL file = one model (table/view)So:stg_customers.sql → stg_customers a table/viewstg_orders.sql → stg_orders a tablemarts: is NOT auto‑created by dbt or SnowflakeJust like staging, you must create the marts folder yourself inside models.----------------------------------------------------------------------------------------------------Step 2: Keep dbt code in Git (mandatory)Your dbt project must live in one of these places:Git repository (recommended)Snowflake Workspace (for development)Snowflake pulls dbt code from Git when deploying. [docs.snowflake.com]This is important because:Git = version controlEnables CI/CDEasy rollback--------------------------------------------------------------------------------------------------------------Step 3: Create Snowflake environmentBefore dbt runs, Snowflake needs:✅ Database✅ Schema✅ Warehouse✅ Role with accessdbt never loads raw data — it only transforms existing tables.-----------------------------------------------------------------------------------------------------------------------Step 4: Install dbt dependencies (one time)If your project uses packages:   dbt deps --commandThis creates the dbt_packages folder.In Snowflake, this can be done:Inside Snowsight WorkspaceOr before deployment via Git------------------------------------------------------------------------------------------------------------------------------Step 5: Deploy dbt project into SnowflakeThis is the most important concept.Snowflake copies your dbt code into an internal object:SQL: CREATE OR REPLACE DBT PROJECT my_db.dbt_schema.my_projectFROM '@my_git_stage/branches/main';\What this does:Creates a schema-level DBT PROJECTStores code as versioned snapshotsSnowflake now “owns” the dbt project✅ Every deploy = new version (VERSION$1, VERSION$2, …)-------------------------------------------------------------------------------------------------------------------------------------Step 6: Run dbt from Snowflake (no dbt CLI needed)To run models:EXECUTE DBT PROJECT my_db.dbt_schema.my_projectARGS = 'run';To run everything (models + tests):ARGS = 'build';Snowflake internally runs dbt Core.✅ Output tables/views are created in Snowflake✅ Logs available in Snowflake------------------------------------------------------------------------------------------------------------------------------------------Step 7: Schedule dbt using Snowflake TasksYou do not use external schedulers.Example:CREATE TASK daily_dbt_runWAREHOUSE = analytics_whSCHEDULE = 'USING CRON 0 2 * * * UTC'AS EXECUTE DBT PROJECT my_db.dbt_schema.my_projectARGS = 'build';✔ Fully governed✔ Uses Snowflake RBAC✔ Enterprise friendly-----------------------------------------------------------------------------------------------------------------------------------------------Step 8: Monitor runsUse Snowflake features:Task historyQuery historyDBT PROJECT execution logsEverything is visible inside Snowflake UI.-------------------------------------------------------------------------------------------------------------------------------------------Step 9: CI/CD (optional but recommended)Snowflake provides CLI commands like:snow dbt deploysnow dbt executeUsed in:GitHub ActionsPR validationProd deployment pipelines
